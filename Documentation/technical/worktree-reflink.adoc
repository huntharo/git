Existing-worktree re-sharing
===========================

Source and interface
--------------------

This follow-up is stacked on conversion-aware checkout (PR #3), whose head is
0b3b36aee2941de69ca9cdd70cbcef6c761b5189. The implementation tested here is
03864ebb20f91afc1e7ebda23230da09d7ea3019. It does not replace the installed
PwrAgent trial runtime or change application/global settings.

An ordinary writer can break sharing when it rewrites a file. A later no-op
checkout does not write that file, so the checkout clone hook cannot recover
its private allocation. `git worktree reflink [<worktree>]` performs that
physical optimization explicitly. `--dry-run`, `--porcelain`, `-z`, `--verbose`
and `--reflink-source` support inspection and integration. See git-worktree(1)
for the versioned output protocol and exact accounting units.

Successful explicit `reset --hard` also invokes this engine with effective
reflink enablement. Explicit false overrides the source marker. The pass
preserves ordinary reset's resulting bytes and exit status; operational
failures warn, and unsupported cases skip. Soft/mixed reset and no-op
checkout/switch retain their previous behavior. Initial worktree creation
already uses checkout's clone hook: its internal reset is marked through a
private child environment variable and does not perform an additional repair
scan. This avoids charging fresh checkout for the existing-file operation.

APFS repair takes its own index lock and reloads the on-disk index while
holding it before scanning or recording replacement stat data. Reset has
already published its index before this transaction; any cooperating writer
that completed in between is retained. Callers must publish pending index
changes before requesting repair. Dry-run and in-place Linux scans do not
write replacement stats and do not acquire this additional write lock.

Eligibility and integrity
-------------------------

Index/stat identity is normalized identity, not proof of checkout bytes.
Attributes-only EOL changes, `git add` and ordinary refresh can leave a clean
file holding a historical LF, CRLF or mixed representation. Re-sharing uses
the target's actual physical representation; it does not reconvert it.

Before opening target or donor files, the scan uses checkout's directory
checks to reject symlinked or non-directory leading components below each
worktree root. The root prefix may itself resolve through symlinks, matching
ordinary checkout. Creation-time donor selection has the same check. These
pathname checks do not provide descriptor-relative confinement against an
arbitrary concurrent replacement of a parent directory; the existing file
replacement concurrency limits still apply.

The scan skips absent/nonregular/sparse/unmerged/intent-to-add entries and
hardlinked targets. Allocation metadata identifies fully shared files before
any hash, conversion, clone or byte comparison. For private candidates,
`ie_match_stat()` with the existing ignore-valid/skip/fsmonitor and
racy-is-dirty flags establishes the normal stat/non-racy fast path. It does
not read objects, hash target contents, look up conversion attributes or
invoke filters. Known size, type and mode changes resolve dirty eligibility
directly. Stat/racy ambiguity uses normal `index_fd()` content verification;
ambiguous external-filter or working-tree-encoding cases skip conservatively.
No fabricated stat entries or separate verification cache are introduced.

Source selection reuses the marker/config/main-worktree order and existing
source index OID/stat/racy checks. The in-place/replacement operation needs
actual existing bytes, so it avoids checkout-only output-conversion and raw
blob-size gates. Stat-clean filtered/LFS files can share without invoking a
filter, because no new checkout output is inferred from the filter's name.
The source descriptor and source/target path identities are rechecked for
observed changes. Dirty-file exclusion retains ordinary Git's stat-trust
limits; an edit invisible to those checks is not newly guaranteed detectable.
The existing PR2 donor/stat trust remains separate from the stronger donor
verification in PR1; this follow-up does not confer PR1's guarantee.

On Linux, FIDEDUPERANGE compares and shares matching ranges in place under
kernel synchronization with writes. It preserves the inode and actual bytes;
normal target hashing is needed only for ambiguous dirty eligibility, not as
its byte-preservation mechanism. Requests are bounded to 16 MiB and account
for returned progress and a short EOF. Unsupported filesystems, unavailable
donors, differing actual bytes and permissions retain existing contents.
The operation may share a prefix before a later range differs or fails.
The kernel contract is documented in
https://man7.org/linux/man-pages/man2/ioctl_fideduperange.2.html[ioctl_fideduperange(2)].

On APFS, public clone APIs require an absent destination. The engine creates
a donor clone in a private temporary directory beside the target, compares
that clone with the opened target, copies target metadata using public
fcopyfile APIs, verifies ownership/mode/times/xattrs/ACLs, and checks captured
descriptor/path stats before rename. Special flags and set-ID targets skip.
Mode, owner, group, mtime, atime, birth time, xattrs and ACLs are preserved when
verification succeeds, except for the kernel-managed `com.apple.provenance`
xattr. As in checkout's xattr cleanup, this attribute is left to macOS rather
than stripped or forged. Native metadata-copy probes have observed successful
`fcopyfile(COPYFILE_METADATA)` leaving different provenance on the target and
new clone. The verifier therefore ignores exactly this name, including its
presence or absence, while comparing the complete remaining name sets and
every value byte for byte. Quarantine and similarly prefixed names have no
exception. This observation does not establish when macOS behavior changed,
or promise a public interpretation of provenance values.

Inode and ctime change. Under the index lock,
`update_ce_after_write()` records the replacement's actual stat, with normal
index writing/racy handling. Failures do not invent old metadata.
APFS dry-run compares bytes without creating a replacement or testing metadata
copy. Its eligibility and potential reduction remain estimates; an apply can
still skip a candidate with `metadata-unavailable` if metadata cannot be copied
and verified.
The public interfaces are described by Apple's
https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/clonefile.2[clonefile(2)]
and https://github.com/apple-oss-distributions/copyfile/blob/main/copyfile.3[copyfile(3)].

Accepted APFS concurrency contract
----------------------------------

The user selected ordinary Git-style file replacement rather than requiring
an atomic in-place APFS primitive. Do not edit working-tree files through
writable mmap, or retain writable descriptors across replacement. Ordinary
read-only mappings of Git objects/pack files are unaffected. Pre/post stat
checks do not close the interval between the last check and rename; ordinary
writes in that interval can race too. A retained descriptor refers to the old
inode and cannot be redirected by rename. This is not arbitrary active-writer
safety, and Linux's stronger in-place guarantee is not claimed for APFS.

The standalone `contrib/reflink/apfs-reshare-limit.c` reproduces the accepted
limit in independent scratch files. Observed macOS results were:

----
fclonefileat_existing rc=-1 errno=17
fcopyfile_clone_force rc=-1 errno=45 cloned=0
write_before_rename_target_changed=0
open_inode_bytes=BC published_bytes=AA inode_changed=1
----

An already dirtied mapped page changed without the captured mtime/ctime
changing. Clone/rename published the prior bytes while the retained old inode
held the later writes. This evidence is separate from regressions that detect
ordinary target writes, source writes, source/target path replacement and a
concurrent edit during the hard-reset repair pass. No private entitlement or
runtime/application replacement is used.

Provenance regression
---------------------

Independent native metadata-copy probes on macOS 27.0.1 (26A434, M5 Max) and
27.2 (26B123, M2 Max) observed this provenance mismatch despite successful
metadata-copy calls and matching copyable stat fields. A target without
provenance could also leave provenance present on the new file. This behavior
therefore predates 27.2; the observations do not establish when it began or
assign publicly guaranteed meanings to the attribute's bytes. Prior successful
same-application fixtures did not distinguish these cases.

The M5 control crossed the packaged signed Git .3 and selected ad-hoc Git .3
as fixture creator and re-share runner under one PwrAgent launcher. All four
combinations created PwrAgent-provenance files and reduced 131,072 private data
bytes to zero. These controls support modeling file-creation/responsible-app
context independently of Git executable signing or the executable's own
provenance. The read-only foreign-provenance metadata-copy probe still failed
strict xattr equality while all ordinary xattrs and copyable stat fields
matched and the existing source's stat remained unchanged. Its scratch content
was independently generated; no existing source data was cloned or re-shared.
Responsible-app launch/creation history is implicated, but the controls do not
reconstruct the actor or scope of historical maintenance. Current shared files
cannot distinguish sharing at checkout from sharing in a later repair pass.

`t2417` runs `contrib/reflink/apfs-reshare-provenance.py`, a native full-command
oracle with a test-only Darwin interposer. It models five provenance states:
different, target-only, clone-only, equal and absent. Each is crossed with
17 metadata scenarios. These are per-file metadata states, independent of
executable identity; the equal-provenance controls deliberately pass.
Positive cases cover both bare files and ordinary
xattrs (including an empty value), a similarly prefixed attribute, and an ACL.
Negative cases cover ordinary value/size/name changes, missing and extra
attributes, quarantine addition/value/removal, name-list/value read errors,
malformed lists, mode, nanosecond mtime and ACL changes. Faults affect only the
temporary clone or the verification syscall replies. File data, copyable
xattrs, ACLs, stat fields and allocation use real disposable APFS files.

The oracle checks exact contents and copyable metadata, actual private data
allocation, inode replacement only on success, and a metadata-only idempotent
second pass. The unchanged PR #10 build fails the otherwise-valid different,
target-only and clone-only provenance cases with `metadata-unavailable`;
the fixed build passes all 85 cases. Existing `t2416` covers dirty files,
concurrent writes and path replacements without altering their protections.

This is controlled syscall interposition, not automated launching of two
responsible applications. It does not attempt to forge real provenance with
`xattr -w`, strip it, or require a particular real provenance value. Native
cross-application observations motivate the model; the deterministic regression
can run without those applications or private worktrees. Reproduce on APFS:

----
make -j4 DEVELOPER=1 NO_RUST=YesPlease NO_GETTEXT=YesPlease NO_TCLTK=YesPlease
python3 contrib/reflink/apfs-reshare-provenance.py --build "$PWD" \
    --root /tmp/new-reshare-provenance-fixture
----

Use a nonexistent scratch root. `--provenance different`, `target-only` or
`clone-only` isolates a pre-fix failure. APFS dry-run remains a byte-comparison
estimate; it does not promise that a later metadata copy will succeed.

Native M2 validation: `t2410` through `t2417` report 204 passes and seven
prerequisite skips (211 total), including all 85 oracle scenarios. The full
`t2413` attributes script passes outside the sandbox, where its fsmonitor
daemon can run. All 261 unit tests pass, as do the developer build, test lints,
Meson test-list check, documentation and builtin checks, Python compilation,
strict interposer compilation and whitespace checks. The test-list registration
and porcelain heading underline are corrected so the standard checks include
`t2417` and accept the worktree documentation.

Authorized existing-worktree control
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

After the scratch tests, the user authorized an actual re-share of one clean,
inactive existing linked worktree on the M2. It had 3,376 index entries, 3,368
tracked regular files, and provenance different from the current launcher.
Both commands ran from the same launcher, without syscall interposition.
The installed PwrGit Git was `2.56.0-dev-pwrgit.3`; the fixed developer build
was from PR #11 commit `4c8c44680b25e563e8459eb91a470474877b700c`.

[cols="3,1,2,2",options="header"]

|PR #11 |2,310 |73,424,896 |36,589,568
|PR #11, second pass |0 |36,589,568 |36,589,568
|===

The installed binary skipped all 2,310 matching candidates with
`metadata-unavailable`. The fixed binary made those files fully shared with
the main checkout, independently confirmed by native private-size and clone-ID
queries. Private file-data allocation fell by 36,835,328 bytes (35.13 MiB).
Total allocated data bytes remained 73,424,896; no claim about volume free
space is made. The remaining 1,058 regular files lacked matching donors;
eight index entries were ineligible. All commands reported zero failures.
The second fixed pass attempted zero clones and replaced zero files.

Per-file SHA-256 hashes for every tracked regular file in both source and
target matched before and after. Target mode, owner/group, flags, link count,
size, nanosecond birth/access/modification times, ACLs and every other xattr
matched; only replaced files could change inode, ctime and OS provenance.
Source copyable metadata also matched apart from access time, which ordinary
donor reads may advance on this live atime mount. HEADs, logical index entries,
symlink targets and clean worktree statuses remained unchanged. No temporary
clone paths remained. Detailed local manifests and command output were kept
outside the repository; private paths and provenance values are omitted here.

Validation and measurements
---------------------------

`DEVELOPER=1 NO_RUST=YesPlease NO_GETTEXT=YesPlease NO_TCLTK=YesPlease`, `-j4`,
default `-g -O2`, no local config.mak/autogen. Existing Ubuntu 24.04 ARM64 in
git-reflink-native uses GCC 13.3.0, Linux 7.0.14-linuxkit, the same developer
options with `NO_RUST=1 NO_GETTEXT=1 NO_TCLTK=1`, and ordinary UID/GID 1000:1000.
Fixtures use actual APFS, existing reflink-enabled XFS /dev/loop0 and btrfs
/dev/loop1. No paid machine, remount or installed-runtime changes were used.

All 4,874 tracked source blobs were checked with normal Git hashing (symlink
contents separately), and the Linux source copy was checked against the exact

Repeated matched APFS costs
--------------------------

The scoped benchmark uses independent ordinary 50fe5cc, PR3 0b3b36aee2 and
implementation 03864ebb20 builds with the native settings above. Two fixtures
contain 2,048 files generated from 64 KiB each: unconverted data and text with
explicit CRLF output (plus its attributes file). Before each timed sample,
the ordinary writer recreates private files; actual file timestamps are aged
and the ordinary index refresh records their real metadata. This preparation
and all contents/allocation checks are outside timing. Shared-scan samples
also perform the initial recovery outside timing.

Five repetitions per cell are shuffled with seed 20261103, using warm caches:
120 timed commands and 24 separate untimed Trace2/allocation controls. All
pass exact digest and actual private-allocation assertions. The timed region
invokes the command with Trace2 disabled. Dry-run includes porcelain output
formatting/capture, so it is not a comparison-only microbenchmark.
