`checkout.defaultRemote`::
	When you run `git checkout <something>`
	or `git switch <something>` and only have one
	remote, it may implicitly fall back on checking out and
	tracking e.g. `origin/<something>`. This stops working as soon
	as you have more than one remote with a _<something>_
	reference. This setting allows for setting the name of a
	preferred remote that should always win when it comes to
	disambiguation. The typical use-case is to set this to
	`origin`.
+
Currently this is used by linkgit:git-switch[1] and
linkgit:git-checkout[1] when `git checkout <something>`
or `git switch <something>`
will checkout the _<something>_ branch on another remote,
and by linkgit:git-worktree[1] when `git worktree add` refers to a
remote branch. This setting might be used for other checkout-like
commands or functionality in the future.

`checkout.guess`::
	Provides the default value for the `--guess` or `--no-guess`
	option in `git checkout` and `git switch`. See
	linkgit:git-switch[1] and linkgit:git-checkout[1].

`checkout.workers`::
	The number of parallel workers to use when updating the working tree.
	The default is one, i.e. sequential execution. If set to a value less
	than one, Git will use as many workers as the number of logical cores
	available. This setting and `checkout.thresholdForParallelism` affect
	all commands that perform checkout. E.g. checkout, clone, reset,
	sparse-checkout, etc.
+
NOTE: Parallel checkout usually delivers better performance for repositories
located on SSDs or over NFS. For repositories on spinning disks and/or machines
with a small number of cores, the default sequential checkout often performs
better. The size and compression level of a repository might also influence how
well the parallel version performs.

`checkout.thresholdForParallelism`::
	When running parallel checkout with a small number of files, the cost
	of subprocess spawning and inter-process communication might outweigh
	the parallelization gains. This setting allows you to define the minimum
	number of files for which parallel checkout should be attempted. The
	default is 100.

`checkout.reflink`::
	If true, commands that write files to the working tree (checkout,
	switch, reset, restore, merge, rebase, worktree add, ...) create a
	file that the worktree's reflink source holds unmodified as a
	copy-on-write clone of it, so the copies share disk space until one
	of them is modified. Eligible files must match the source index's
	normal stat checks and be non-racy. Unconverted clones are not read back
	or hashed. EOL conversions can share when comparison with the ordinary
	checkout output establishes the same physical representation. Racy or
	dirty donors, or disabled ctime/stat checks, use the ordinary writer.
	As with Git's normal stat
	cache, edits invisible to those checks can be missed; such a donor
	can supply bytes that differ from a checkout from the object database.
	Files subject to a filter driver, `ident` or `working-tree-encoding`
	on checkout use the ordinary writer. If false, cloning
	is disabled, even in worktrees created with `git worktree add
	--reflink` (only that command's own initial checkout still clones).
	If unset, worktrees created with `--reflink` clone and others do
	not. A value that is not a boolean disables cloning, with a
	warning. Cloning is supported on APFS (macOS) and on btrfs, XFS,
	bcachefs and overlayfs (Linux); elsewhere, across filesystems, and
	on Windows, files are silently written as usual. See
	linkgit:git-worktree[1].

`checkout.reflinkSource`::
	The worktree that `checkout.reflink` clones files from, given as a
	worktree name or path, as for `git worktree move` (prefer a name or
	an absolute path: relative paths are relative to the top of each
	worktree). A worktree created with `git worktree add
	--reflink-source` uses the worktree given there instead, while it
	exists. Defaults to the main worktree. A candidate that is missing,
	bare, or the current worktree itself is skipped in favour of the
	next one; a reflink source on another filesystem means nothing is
	cloned.
